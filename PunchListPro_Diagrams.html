05
Actors — Primary & Secondary
Who interacts with PunchList Pro and why

Primary Actors — Drive core use cases

Facility Admin
role: "admin"
Creates projects, formally closes punch items, manages the entire system. Only actor who can DELETE pins and set status=closed.
General Contractor
role: "general_contractor"
Manages sheets, assigns pins to subs, reviews work, escalates to admin review. Central to the approval workflow.
Subcontractor
role: "sub_contractor"
Receives assigned punch items, moves them to In Progress, submits for contractor review, uploads photos. Primary field user.
Field Inspector
role: "field_inspector"
Creates and updates pins on-site. Works offline-first via IndexedDB. Daily active user in the field.

Secondary Actors — Participate but don't drive workflow

Architect
role: "architect"
Reviews sheets, views and creates pins, exports reports. Observes and verifies but doesn't manage work assignments.
Owner
role: "owner"
Read-only viewer of project status and reports. Consumes outputs, doesn't create or modify data.

System (Non-Human) Actors

ActorTypeRole in System
Supabase AuthExternal SaaSVerifies JWT tokens on every API request
Socket.IO ServerInternalBroadcasts real-time pin/status updates to all clients
IndexedDB (Dexie)InternalOffline cache for Field Inspector when connectivity is lost
Sync QueueInternalBatches offline mutations and replays when back online via /api/sync/batch

Sequence Diagram — Login Flow
Supabase auth to backend token exchange to user profile
sequenceDiagram actor User participant Browser as React Browser participant SupaJS as Supabase JS Client participant SupaCloud as Supabase Cloud Auth participant FastAPI as FastAPI Backend participant DB as Database User->>Browser: Enter email + password, click Login Browser->>SupaJS: signInWithPassword(email, password) SupaJS->>SupaCloud: POST /auth/v1/token SupaCloud-->>SupaJS: session with access_token and user SupaJS-->>Browser: session Browser->>FastAPI: POST /api/auth/supabase-callback with Bearer token FastAPI->>SupaCloud: GET /auth/v1/user to verify token SupaCloud-->>FastAPI: supabase_uid and email FastAPI->>DB: SELECT from users WHERE supabase_uid matches DB-->>FastAPI: user row with role and company_id FastAPI-->>Browser: id, name, role, company_id Browser->>Browser: Store user in React state Browser-->>User: Redirect to Dashboard
Fallback: If Supabase unavailable — POST /api/auth/login — bcrypt password check — local JWT returned.

State Machine — Pin Lifecycle
All valid status transitions and which role drives each one
stateDiagram-v2 [*] --> open : Pin Created by authorized role open --> in_progress : Sub or GC or Inspector starts work open --> closed : Admin closes directly in_progress --> submitted_for_contractor_review : Subcontractor submits work in_progress --> submitted_for_admin_review : GC escalates directly in_progress --> closed : Admin closes directly submitted_for_contractor_review --> in_progress : GC sends back for rework submitted_for_contractor_review --> submitted_for_admin_review : GC approves and escalates submitted_for_admin_review --> in_progress : Admin rejects and sends back submitted_for_admin_review --> closed : Admin formally closes closed --> [*]
Critical rule: Only the Facility Admin can set status = closed. This is the most important permission boundary in the entire system.
